# ADR-003 — Apache Kafka como backbone de eventos

**Estado:** Sustituido como decisión inicial por [ADR-010](ADR-010.md). **Fuente:** propuesta española p. 7; caso inglés pp. 2–8.

## Contexto y criterios

Varias sondas pueden producir ráfagas; sesiones y dispositivos tienen consumidores y ritmos diferentes. Se necesitan desacoplamiento, retención/replay acotados, particionado y recuperación tras caída del destino.

## Decisión propuesta

Un clúster Kafka privado con topics separados `sessions.detected` y `devices.detected`, contratos versionados, ACL por identidad y clave de partición que conserve el orden necesario. Punto de partida de HA para comprobar: tres brokers, replicación 3, `min.insync.replicas=2`, productor `acks=all` e idempotencia. Particiones, retención y nodos definitivos dependen de pruebas; Kafka no es archivo histórico.

## Alternativas y por qué no ahora

| Alternativa | Ventaja | Motivo para no seleccionarla |
|---|---|---|
| HTTP directo de cada sonda a API | Operación inicial sencilla | Traslada picos y caídas al backend, exige buffer/replay propios y acopla captura a disponibilidad de API. |
| Dos brokers o buses por dominio | Aislamiento | Duplica operación sin una necesidad demostrada de separación física. |
| RabbitMQ u otra cola tradicional | Enrutamiento flexible | El caso prioriza log particionado, múltiples consumidores y replay temporal; habría que construir/validar equivalentes. |

## Consecuencias y validación

Mayor coste operativo de brokers, particiones y observabilidad. Medir pérdida en sonda, lag, throughput sostenido/pico y recuperación; ensayar caída de broker y ventana de retención. No interpretar tres brokers como dimensionamiento final.

Para una eventual replicación entre clústeres o migración, consultar la [nota de vigilancia sobre KIP-1279](../vigilancia-kafka-mirroring.md); no modifica esta decisión histórica ni introduce Kafka en el MVP.
