# ADR-010 — Arquitectura inicial mínima y evolución por pruebas

**Estado:** Aceptado como dirección de diseño de la primera entrega de producción (24-09-2026). [ADR-013](ADR-013.md) sustituye las cifras de piloto de [ADR-012](ADR-012.md); [ADR-014](ADR-014.md) define [S00](../../development/slices.md#s00) como modelo que habilita PostgreSQL provisional y S17 como puerta empírica. Las [brechas de producción](../../roadmap-gaps.md#validaciones-para-liberar-la-primera-entrega-de-producción) conservan las evidencias pendientes. **Sustituye en la ruta inicial:** ADR-003 a ADR-008; limita ADR-001 y ADR-009. No invalida los análisis anteriores: registra el cambio de criterio.

## Contexto

El [caso práctico inglés](../../references/processed/network-monitoring.md) es un ejercicio con variantes y sugerencias, incluidas Kafka, base relacional, Elasticsearch/Kafka Connect, DLL, EJBCA y Keycloak. El [análisis español](../../references/processed/arquitectura-monitorizacion-red.md) propone Kafka/Avro/Registry, ClickHouse + PostgreSQL y mTLS universal. El usuario indicó expresamente que las tecnologías de ambos documentos son sugerencias, no requisitos de implementación. Ninguno demuestra tasa por segundo, retención, consultas, concurrencia, RPO/RTO ni plataforma ya disponible. El usuario pide valorar equipo de seis personas .NET/Angular, presupuesto medio, calidad y coste operativo. El objetivo es aprender y justificar arquitectura mientras se entrega un sistema útil, sin redundancia de datos ni componentes preventivos.

## Decisión

Ruta candidata: sonda con `tshark` y adaptador .NET; lotes de metadatos con IDs estables a una API de ingestión interna; PostgreSQL como primer candidato para bandeja durable, sesiones e inventario; worker .NET de proyección; API modular ASP.NET Core; Angular para usuarios. [S00](../../development/slices.md#s00) modela esta elección provisional; S17 decide si PostgreSQL cumple como almacén de sesiones de 30 días antes de liberar. Se mantiene un único histórico autoritativo, sin copia completa permanente en otro motor. Las altas manuales y observaciones automáticas comparten reglas de dominio. Cada sonda tiene spool dimensionado, reintentos y pérdida observable al agotarse. Sin PCAP persistido por defecto. Despliegue privado sobre plataforma apta.

Esta ruta reduce coste de instalación, supervisión, upgrades, backups, restauraciones, certificados y contratos para un equipo pequeño. No demuestra que PostgreSQL alcance 10 M de sesiones/día, 300 M en 30 días o 20 consultas concurrentes: **S00 modela la capacidad y habilita su uso provisional**; S17 ejecuta el ensayo integrado con datos representativos antes de liberar ([ADR-014](ADR-014.md)). PostgreSQL permite particionado declarativo y poda de particiones ([manual](https://www.postgresql.org/docs/current/ddl-partitioning.html)); el índice físico se define con filtros reales.

## Trazabilidad de sugerencias y alternativas

| Sugerencia | Decisión inicial y motivo | Prueba o condición para cambiar |
|---|---|---|
| `tshark` | Adoptar como extractor de campos inicial: evita escribir decodificadores. Hay que construir correlación de sesiones, controlar versión/formatos y medir descartes ([manual](https://www.wireshark.org/docs/man-pages/tshark.html)). | Si su CPU, pérdidas o privilegios no cumplen ensayo, evaluar captura especializada. |
| .NET y Angular | Adoptar por experiencia declarada del equipo y UI interna; el caso permite otras pilas. Mantener fronteras y pruebas, no microservicios por entidad. | Cambios de habilidades, integración o rendimiento demostrados. |
| Kafka (ambos documentos) | Diferir. Una API de ingestión con spool y bandeja de entrada cubre una sola ruta de datos y evita operar brokers. HTTP directo sin spool sería frágil; el diseño **sí** tiene amortiguación finita. Kafka aporta particiones y replay cuando se necesiten ([diseño oficial](https://kafka.apache.org/documentation/)). | Consumidores independientes con replay, desconexión superior al spool o ingesta medida superior a la ruta; exigir dueño de brokers, retención, ACL y HA. |
| Avro y Schema Registry (análisis español) | Diferir junto con Kafka. Contrato JSON versionado con validación en API y pruebas de compatibilidad es suficiente entre sensor y servidor propios. | Productores de distintas versiones, alto coste de payload o múltiples consumidores independientes; medir coste de Registry. |
| DLL de dominio compartida (caso inglés) | Rechazar entre sensor y backend: despliegues y evolución acoplados. Compartir reglas internas dentro del backend modular y contratos de red versionados. | Monorrepositorio con cadencia idéntica y ventaja medida que supere el acoplamiento. |
| ClickHouse + PostgreSQL (análisis español) | PostgreSQL es primer candidato, sujeto a S00. Dos motores son legítimos si sesiones analíticas e inventario transaccional tienen cargas incompatibles, pero duplican operación antes de medir. ClickHouse está diseñado para analítica en tiempo real ([casos oficiales](https://clickhouse.com/use-cases)); eso no demuestra su necesidad aquí. | Si índices, particiones y límites de consulta no cumplen p95/coste con 30 días y escritura concurrente, comparar ClickHouse con el mismo perfil; migrar sesiones por etapas y retirar su copia previa. |
| Elasticsearch + Kafka Connect (caso inglés) | Rechazar inicialmente: indexar el mismo histórico crea doble retención, reconciliación y recuperación. Connect sirve a un sink cuando éste existe; no es un requisito funcional. | Búsqueda libre sobre texto o integración externa necesaria y demostrada, con responsable y presupuesto de datos duplicados. |
| Consola que llama `POST /devices` (caso inglés) | Rechazar salto HTTP interno: worker y API usan el mismo módulo de dominio y transacciones. | Consumidor externo con ciclo de vida y frontera propia. |
| EJBCA y mTLS en todos los saltos (análisis español) | Confirmar con seguridad el nivel requerido. Adoptar TLS validado y mTLS sensor→ingestión; ampliar mTLS según frontera y mandato. Reutilizar PKI corporativa compatible; EJBCA solo si falta CA apta y existe dueño de ciclo de vida ([EJBCA](https://docs.keyfactor.com/ejbca/latest/)). Certificado de navegador universal añade soporte significativo. | Modelo de amenaza, política interna o regulación exige autenticación mutua adicional; probar emisión, rotación y revocación. |
| Keycloak (ambos) | Reutilizar IdP OIDC corporativo antes de desplegar otro. Keycloak es opción autónoma válida si no existe IdP apto ([documentación oficial](https://www.keycloak.org/documentation)). RBAC siempre se aplica en API; mTLS identifica máquina, no persona. | Compatibilidad, soporte de roles/auditoría y coste de operación del IdP disponible. |
| Servicios, Kubernetes y observabilidad | API + worker + sensor son separaciones por ubicación/privilegios. Reutilizar plataforma y telemetría corporativas; instrumentar con OpenTelemetry ([documentación](https://opentelemetry.io/docs/)). No introducir orquestador o pila paralela. | Réplicas/aislamiento y capacidades operativas medidas que lo justifiquen. |

## Consecuencias y calidad

La [nota sobre replicación nativa entre clústeres Kafka](../vigilancia-kafka-mirroring.md) queda como referencia para una posible evolución de Kafka; no altera la elección inicial.

La ruta candidata limita replay y aislamiento de ingesta; el spool y la bandeja consumen disco y exigen cuotas, alertas y procedimientos dimensionados en [ADR-013](ADR-013.md). El worker debe ser idempotente; una respuesta ambigua no equivale a pérdida. La captura SPAN/TAP también puede perder paquetes y debe exponerse como métrica. Sesiones e inventario en una base compartirían recursos; S00 estima ese riesgo y S17 mide la contención durante consulta e ingesta. Los objetivos de ADR-013 aún no son SLO corporativos aprobados ni resultados medidos.

## Coste y condiciones de validación

Antes de adoptar componentes adicionales, comparar horas mensuales de operación/guardia, nodos y discos, copias, recuperación, upgrades, certificados y formación. No se inventa presupuesto monetario sin precios internos. [ADR-013](ADR-013.md) define el perfil de producción y la prueba previa; redes mide volumen y pérdidas, producto y seguridad ratifican retención/consultas, y operación demuestra IdP, copias y recuperación. Las [validaciones de liberación](../../roadmap-gaps.md#validaciones-para-liberar-la-primera-entrega-de-producción) indican responsables y evidencia. La elección de diseño no demuestra rendimiento ni aprueba políticas o infraestructura. Si la evidencia contradice la ruta, registrar el cambio en un ADR sucesor con coste y consecuencias.
