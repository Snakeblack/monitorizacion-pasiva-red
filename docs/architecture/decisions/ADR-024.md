# ADR-024: La dirección de metadatos OIDC puede diferir del emisor

- Status: accepted (consolidado el 2026-10-07 por instrucción de la persona responsable del producto, con la evidencia indicada)
- Change: producto-monitorizacion-final
- Date: 2026-10-07
- Complementa: [ADR-018](ADR-018.md) y [ADR-002](ADR-002.md) (zonas privadas). Origen: [ADR-022](ADR-022.md).

## Context
El API valida el emisor contra `Identity:Authority` y, hasta ahora, descargaba el documento de descubrimiento de esa misma dirección. Dos restricciones reales impiden usar una sola dirección en el laboratorio, y la primera también puede darse en producción:
- el nombre del emisor es el que ve el navegador (la SPA exige HTTPS o loopback), que puede no ser alcanzable desde el API, o no ser la ruta que el API debe usar hacia el IdP (zonas privadas, [ADR-002](ADR-002.md); un balanceador o proxy en medio);
- dentro del contenedor del API, `127.0.0.1` no es Keycloak.

## Decision
`Identity:MetadataAddress` es una opción del API, **opcional**, con la dirección del documento de descubrimiento (`JwtBearerOptions.MetadataAddress`). Sin ella, el documento se lee de `Identity:Authority` como hasta ahora.
- **No cambia a quién se confía.** El emisor aceptado sigue siendo `Identity:Authority` (`ValidIssuer`), la audiencia sigue siendo `Identity:Audience` y la firma se valida con las claves del documento leído. Quien controle esa dirección controla las claves, por lo que se le exige lo mismo que a la autoridad.
- **Mismas reglas que la autoridad:** URL absoluta, HTTPS (HTTP solo en Development/Testing) y sin credenciales (`user:pass@`). Si no cumple, el host no arranca, igual que ante un error de configuración de la autoridad.
- **En Keycloak** se pide `KC_HOSTNAME` (emisor y endpoints de navegador) y `KC_HOSTNAME_BACKCHANNEL_DYNAMIC=true`: JWKS y token siguen el host con el que se llamó, así que el API los alcanza como `keycloak:8080` mientras el emisor sigue siendo `127.0.0.1:8081`.

## Alternatives
- **Compartir el espacio de red de Keycloak con el API** (`network_mode: service:api`) para que ambos vean `127.0.0.1`: no toca el código, pero acopla dos contenedores y no se parece a ningún despliegue real, así que no probaría lo que se despliega.
- **Resolver `keycloak` a loopback en el navegador de pruebas:** la SPA rechaza un emisor HTTP que no sea loopback; relajar esa barrera de producción para satisfacer al laboratorio la debilita.
- **Un emisor y un documento de descubrimiento con el mismo nombre, sin opción:** es el caso habitual y sigue siendo el valor por defecto; la opción solo existe para cuando no se puede.
- **Aceptar emisores múltiples:** amplía a quién se confía; descartado.

## Evidence
- 4 pruebas nuevas en `OidcIdentityTests` (rojas antes de la implementación, verdes después): la dirección se aplica sin alterar `ValidIssuer` ni `Authority`; sin ella se usa la autoridad; una dirección HTTP en producción, relativa, mal formada o con credenciales impide el arranque; en Testing se acepta HTTP.
- Contra Keycloak real: el descubrimiento pedido como `keycloak:8080` devuelve `issuer` y endpoints de navegador en `127.0.0.1:8081` y `jwks_uri`/`token_endpoint` en `keycloak:8080`; el API valida tokens emitidos con el emisor del navegador (7/7 en el E2E).

## Cost and ownership
Una propiedad de configuración y su validación. Responsable: la persona responsable del producto.

## Consequences
- Una `MetadataAddress` errónea en producción detiene el arranque (falla cerrado) o, si apunta a un proveedor equivocado pero válido, hace que se confíe en sus claves: debe revisarse como se revisa la autoridad.
- No se ha probado con un IdP distinto de Keycloak ni con TLS real (pendiente de 3.2).

## Reversion
Quitar la propiedad de `IdentityOptions` y su uso en `IdentityRegistration`. Sin ella, el emisor y la dirección de descubrimiento deben ser alcanzables con el mismo nombre desde el API.
