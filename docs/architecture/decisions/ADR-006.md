# ADR-006 — Workers .NET explícitos para consumo y persistencia

**Estado:** Sustituido como decisión inicial por [ADR-010](ADR-010.md). **Fuente:** propuesta española pp. 6, 8; caso inglés pp. 8–10.

## Contexto y criterios

Se debe controlar cuándo confirmar un offset de Kafka respecto a la persistencia, sobre todo tras respuesta ambigua. Las sesiones requieren lotes hacia ClickHouse; las observaciones de dispositivos, reglas de inventario en PostgreSQL. El caso ampliado muestra consola de integración y Kafka Connect hacia Elasticsearch; esos mecanismos responden a otro destino y otra topología.

## Decisión propuesta

Session Worker .NET valida Avro, agrupa lotes repetibles e inserta en ClickHouse; confirma offsets solo tras escritura durable. Device Worker separado procesa observaciones y aplica upsert bajo reglas de dominio en PostgreSQL. Ambos tienen reintentos con backoff, DLQ y métricas. En fallo ambiguo, se reintenta el mismo lote con token derivado de topic/partición/rango de offsets. Semántica **al menos una vez**; reconstrucción histórica fuera de la ventana de deduplicación mediante carga nueva y cambio validado.

## Alternativas y por qué no ahora

| Alternativa | Ventaja | Motivo para no seleccionarla inicialmente |
|---|---|---|
| Motor Kafka de ClickHouse | Menos proceso propio | El control de durabilidad y sincronía de offset exige configuración y pruebas minuciosas; no satisface por sí solo reglas de validación/DLQ previstas. |
| Kafka Connect sink | Conectores estándar, adecuado para Elasticsearch del caso | El destino propuesto es ClickHouse y se necesita semántica de lotes, token y cuarentena específica; un sink genérico puede ocultar ese orden de confirmación. |
| Consola que llama `POST /devices` | Reutiliza validación API | Agrega salto HTTP, autenticación y dependencia de disponibilidad de API para un flujo interno; la validación de dominio puede compartirse dentro del backend modular. |

## Consecuencias y validación

Más código de integración propio, a cambio de control observable sobre offsets y fallos. Probar caídas entre inserción y commit, DLQ durable, rebalances, replay y deduplicación finita. Especificar las reglas comunes de alta manual y automática antes de implementarlas.
