# ADR-007 — Modelo físico y retención temporal de sesiones

**Estado:** Sustituido como decisión inicial por [ADR-010](ADR-010.md). **Fuente:** propuesta española pp. 8, 10; caso inglés pp. 3–4.

## Contexto y criterios

El volumen total aislado no determina coste ni latencia; importan tasa, cardinalidad, filtros, retención y concurrencia. La propuesta espera búsquedas por tiempo, sitio, IP y protocolo, pero aún faltan consultas y datos reales.

## Decisión propuesta

Columnas explícitas y tipadas en ClickHouse; tiempos en UTC; particiones temporales para ciclo de vida y TTL; ordenación MergeTree basada en filtros demostrados. Evitar partición por IP, dispositivo o identificadores de alta cardinalidad. Añadir rollups/materialized views solo para consultas recurrentes medidas. API impone rango temporal, paginación, selección de columnas y tiempo máximo.

## Alternativas y por qué no ahora

| Alternativa | Ventaja | Motivo para no seleccionarla |
|---|---|---|
| Guardar todo como JSON | Esquema flexible | Pierde tipos y dificulta optimizar columnas/filtros críticos. |
| Particionar por IP, dispositivo o cada sitio | Aparente poda fina | Cardinalidad alta aumenta partes y coste de merges; no equivale a mejor ordenación para consultas. |
| Detalle indefinido y agregados preventivos | Responde a cualquier horizonte aparente | Coste no acotado y trabajo de mantenimiento sin patrón de consulta validado. |

## Consecuencias y validación

Elegir orden físico exige muestras reales y quizá migración futura. Medir bytes comprimidos/fila, partes/merges, p95 de consultas y TTL; acordar retención antes del esquema definitivo. El particionado gestiona principalmente ciclo de vida, no garantiza consultas rápidas por sí solo.
