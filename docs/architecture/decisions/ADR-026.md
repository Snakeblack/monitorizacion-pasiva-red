# ADR-026: Las claves de firma se releen cada 5 minutos, una clave retirada se deja de aceptar y una clave nueva se acepta a la primera

- Status: propuesto (pendiente de confirmar por la persona responsable del producto)
- Change: producto-monitorizacion-final
- Date: 2026-10-07
- Complementa: [ADR-018](ADR-018.md) y [ADR-025](ADR-025.md). Origen: [ADR-022](ADR-022.md), que dejó sin validar la rotación de claves en caliente ni la caída del proveedor.

## Context
El API valida los tokens con las claves que descarga del proveedor y las guarda en memoria. Tres comportamientos de la configuración por defecto de la librería, medidos contra Keycloak real y en proceso, no cumplían lo que pide [REQ-identidad-y-acceso](../../../openspec/changes/producto-monitorizacion-final/specs/identidad-y-acceso/spec.md) (las claves siguen la rotación del proveedor y un token que no se puede verificar no concede identidad):

1. **Una clave nueva rebotaba al primer usuario.** Al añadir una clave de firma en Keycloak, la primera petición con un token firmado con ella recibía 401 y el SPA cerraba la sesión: el manejador de JwtBearer solo pide un refresco, no reintenta esa petición, y el gestor de configuración refresca en segundo plano mientras sigue sirviendo las claves antiguas.
2. **Una clave retirada se seguía aceptando.** Medido: tras retirar la clave en Keycloak, el API siguió aceptando tokens firmados con ella más de **481 s** después (la medición se detuvo ahí, con el token todavía sin caducar y el intervalo automático de 5 minutos ya vencido), y la misma prueba en proceso lo reproduce en tres segundos tras releer el conjunto de claves. La causa es la configuración «última buena conocida» de la librería: se conserva la última configuración con la que se validó un token y se usa de reserva si la actual falla, durante 12 horas por defecto. Para claves rotadas es una ventaja; para claves **retiradas** (una clave comprometida, la razón de retirarla) es lo contrario. Además el intervalo automático por defecto del API era de **1 hora**.
3. **Con el proveedor caído** hay que saber si un refresco fallido borra las claves ya fiables.

## Decision
- **`Identity:KeysRefreshMinutes`** (por defecto **5**, entre 5 y 60; 5 es el mínimo que admite la librería) fija cada cuánto se relee el conjunto de claves aunque ningún token nombre una clave desconocida. Antes estaba fijo en 60 minutos. Un valor fuera de rango impide el arranque.
- **Se desactiva la configuración «última buena conocida»** (`LastKnownGoodLifetime = 0`): una clave que el proveedor ya no publica deja de aceptarse en cuanto el API relee el conjunto de claves. La resiliencia ante un proveedor caído no depende de ella: un refresco fallido conserva la configuración **vigente** (probado).
- **Un `kid` desconocido provoca una relectura inmediata y se reintenta esa misma petición** (`SigningKeyRefresher`), con los mismos parámetros de validación; si no tiene éxito, la petición termina en 401 como antes. Está acotado: la espera máxima es de 3 s; las peticiones concurrentes comparten la misma relectura; no se inicia otra antes de un minuto desde la anterior (el suelo `RefreshInterval` de la librería), de modo que un flujo de tokens falsos cuesta como mucho una petición lenta por minuto y el resto se rechazan al instante. El tiempo de espera del canal con el proveedor baja de 60 a 10 s.
- **Procedimiento de rotación** (para operación): publicar la clave nueva con prioridad menor, esperar a que el API la haya leído (hasta `KeysRefreshMinutes`), subir su prioridad y, pasado el tiempo de vida de los tokens, retirar la anterior. Si se activa directamente, funciona (el primer token con la clave nueva se acepta), salvo que otra relectura forzada haya ocurrido hace menos de un minuto: entonces el primer usuario es rechazado hasta que pase ese suelo.

## Alternatives
- **Dejar los valores de la librería** (1 h de intervalo, 12 h de configuración de reserva): no se puede retirar una clave comprometida en menos de medio día sin reiniciar el API. Descartado por la medición.
- **Un resolvedor de claves propio con relectura síncrona:** bloquea un hilo por petición mientras espera al proveedor y es el patrón más fácil de usar para agotar el servidor con tokens falsos. Se prefirió esperar de forma asíncrona, compartida y acotada.
- **Reiniciar el API para retirar una clave:** válido como medida de emergencia (y sigue siéndolo), pero no como mecanismo de operación.
- **Notificación del proveedor (evento de administración) en lugar de sondeo:** acopla el proveedor al API y añade un canal más que proteger; el sondeo cada 5 minutos cuesta una petición pequeña.
- **Intervalo inferior a 5 minutos:** la librería lo rechaza (`IDX10108`); cambiarlo exigiría tocar un valor estático global.

## Evidence
- **En proceso, contra un proveedor HTTPS real** (`OidcProviderTlsTests`, 5 pruebas nuevas): una clave añadida se acepta en la primera petición y la anterior sigue valiendo; 20 tokens falsos con un `kid` desconocido cuestan al proveedor como mucho una petición extra; un token falso que reutiliza el `kid` rotado con otra firma sigue en 401; un proveedor parado no borra las claves fiables; una clave retirada deja de aceptarse tras releer (roja antes de desactivar la configuración de reserva, verde después). `OidcIdentityTests`: valor por defecto, valor configurado y rango.
- **Contra Keycloak 26.7.5 real** (`identity-rotation.spec.mjs`, 2/2, también en CI): se añade una clave RSA de prioridad mayor con el API en marcha; el primer token firmado con ella se acepta sin reiniciar y el anterior sigue valiendo; se **para Keycloak**, se fuerza un refresco fallido con un `kid` desconocido y el token firmado con una clave ya fiable sigue aceptándose; tras volver a arrancar, todo sigue sin intervención.
- **Retiro de una clave, medido contra Keycloak real** (`identity-key-retirement.spec.mjs`, manual con `E2E_SLOW=1`, ≈7 min): con la configuración de reserva desactivada la clave retirada dejó de aceptarse a los **333 s** (el token seguía sin caducar; el límite de la prueba es 390 s: los 300 s del intervalo, el sondeo cada 15 s y la petición que dispara la relectura). Sin la corrección, la misma prueba seguía aceptándola a los 481 s.
- Suite .NET completa: 494/494.

## Cost and ownership
Dos propiedades de configuración y una clase de unas 50 líneas. Una petición pequeña al proveedor cada 5 minutos y, en una rotación, una relectura inmediata. Responsable: la persona responsable del producto con operación de identidad, que debe aplicar el procedimiento de rotación.

## Consequences
- Una clave retirada deja de aceptarse en como mucho `KeysRefreshMinutes` (más el suelo de un minuto si hubo una relectura reciente), no en horas. Sigue valiendo hasta entonces: ante una clave comprometida hay que retirarla **y** reiniciar el API si no se puede esperar.
- Sin la configuración de reserva, si el proveedor publica por error un conjunto de claves vacío o sin la clave en uso, los usuarios quedan sin acceso (401, falla cerrado) hasta que se corrija, en lugar de seguir con la configuración anterior. Se acepta porque es la misma propiedad que se quiere para una clave comprometida.
- La primera petición con un `kid` desconocido por minuto puede tardar hasta 3 s en recibir el 401. Es el precio de aceptar una clave nueva a la primera sin exponer al API.
- El suelo de un minuto entre relecturas forzadas no se puede acortar sin cambiar la librería; una rotación inmediatamente después de otra relectura rebota una vez al primer usuario (procedimiento de rotación arriba).
- Un perfil de producción de Keycloak (otra base de datos, otro ritmo de rotación) no se ha probado.

## Reversion
Quitar `KeysRefreshMinutes` (volviendo a 1 hora fija), la línea de `LastKnownGoodLifetime`, `SigningKeyRefresher` y el reintento de `OnAuthenticationFailed`. El API vuelve a la conducta por defecto de JwtBearer, con las consecuencias del apartado Context.
