# ADR-001 — Backend modular .NET y despliegues por carga

**Estado:** Revisado; .NET modular es la elección inicial, con despliegues separados según carga o permisos. **Fuente:** propuesta española p. 7; caso inglés pp. 3–5.

## Contexto y criterios

La propuesta declara equipo de seis personas con experiencia .NET/Angular. API, sesiones e inventario comparten reglas, pero consulta e ingestión tienen perfiles de carga y permisos diferentes. Importan cohesión, velocidad de desarrollo, aislamiento de carga y coste de operación.

## Decisión propuesta

Usar una base de código .NET con módulos de API, ingestión, sesiones e inventario. Una API y un worker bastan al inicio; separar el proceso de ingestión si los privilegios o la carga lo exigen. No crear un worker por entidad. La sonda es independiente por ubicación y privilegios. Las fronteras se expresan en interfaces y contratos HTTP versionados, sin compartir entidades internas como contratos de red.

## Alternativas y por qué no ahora

| Alternativa | Ventaja | Motivo para no seleccionarla inicialmente |
|---|---|---|
| Microservicio por entidad | Despliegue autónomo | Multiplica repositorios, contratos, operaciones y coordinación para seis personas; no hay evidencia de autonomía de equipos por entidad. |
| Único proceso de captura, UI, API y workers | Menos despliegues | Acopla privilegios de captura, consulta y escritura; un pico o fallo de ingestión afecta la API. |
| Backend Java/Python/Node | Opciones válidas en el caso inglés | La experiencia .NET declarada reduce curva de aprendizaje y permite dedicar esfuerzo a datos/seguridad; no hay requisito que obligue otra plataforma. |

## Consecuencias y validación

Menos duplicación y despliegue por caudal a cambio de disciplina de módulos y pipelines para varios roles. Confirmar estructura, testabilidad y que escala cada worker sin alterar API. Revisar si cambian equipo, dominios o independencia de despliegue.
