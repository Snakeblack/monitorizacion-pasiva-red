# ADR-025: El API confía en el TLS del proveedor de identidad por una lista de CA propia, sin mTLS hacia él

- Status: propuesto (pendiente de confirmar por la persona responsable del producto)
- Change: producto-monitorizacion-final
- Date: 2026-10-07
- Complementa: [ADR-018](ADR-018.md), [ADR-024](ADR-024.md) y [ADR-002](ADR-002.md) (zonas privadas). Origen: [ADR-022](ADR-022.md), que dejó sin validar TLS hacia Keycloak.
- Relacionado: [ADR-026](ADR-026.md) (refresco y rotación de claves), [ADR-010](ADR-010.md) (alcance de mTLS).

## Context
El API descarga el documento de descubrimiento y el conjunto de claves (JWKS) del proveedor de identidad, y quien controle ese canal controla en qué claves se confía: es tan sensible como la propia autoridad ([ADR-024](ADR-024.md)). Hasta ahora el laboratorio lo ejercía por HTTP, de modo que ni la cadena de certificados, ni el nombre, ni la vigencia, ni la confianza en una CA privada se habían probado nunca. En un despliegue privado ([ADR-002](ADR-002.md)) el certificado del proveedor lo emite casi siempre una CA interna, que el sistema operativo del contenedor del API no conoce.

## Decision
- **`Identity:TrustedCaPaths`**: lista opcional de ficheros (PEM o DER) con las CA que pueden firmar el certificado del proveedor. Si está vacía se aplican las raíces de la plataforma, como a cualquier cliente HTTPS.
- **Sustituye, no suma, las raíces del sistema, y solo para ese canal** (descubrimiento y claves): un certificado emitido por cualquier otra CA se rechaza aunque la máquina confíe en ella. El resto del tráfico saliente del API no cambia.
- **Se sigue exigiendo** que el certificado cubra el nombre al que se conecta el API (la `MetadataAddress` o, sin ella, la autoridad), que esté vigente y que sirva para autenticar servidores (EKU `serverAuth`). No se comprueba revocación del certificado del proveedor: la CA se fija por configuración y lo que se descarga es público por diseño.
- **Falla cerrado:** un fichero ausente, ilegible, que no sea un certificado (por ejemplo, solo una clave privada) o una ruta en blanco impide el arranque. Un canal TLS que no se puede establecer deja sin claves fiables, y nadie se identifica (401), como ya ocurría con un proveedor caído.
- **No se adopta mTLS del API hacia el proveedor.** El API no presenta certificado de cliente a Keycloak: lo único que pide son dos documentos públicos, y [ADR-010](ADR-010.md) limita mTLS a la frontera sonda→ingestión y a donde un modelo de amenaza o una norma lo exijan. Si el proveedor se despliega tras un proxy que exija mTLS, se añade entonces un certificado de cliente a este mismo manejador.
- **Laboratorio:** `scripts/lab/prepare.ps1` emite una CA desechable y un certificado de servidor para Keycloak (nombres `keycloak`, `localhost` y `127.0.0.1`) en `lab-secrets/tls/` (ignorado por git). Keycloak sirve HTTPS en el puerto 8443 de la red de Compose, sin publicar, y el API lee el descubrimiento de `https://keycloak:8443/…` con la CA del laboratorio como único ancla. Al navegador se le publica el HTTP de loopback `http://127.0.0.1:8081`, que el SPA admite por ser loopback, de modo que **ningún navegador necesita confiar en la CA** y el emisor es `http://127.0.0.1:8081/realms/monitoring` (`KC_HOSTNAME_BACKCHANNEL_DYNAMIC` hace que los endpoints de canal trasero sigan el esquema y el host de la petición). El realm usa `sslRequired: external`.

## Alternatives
- **Instalar la CA en el almacén del sistema de la imagen del API** (`SSL_CERT_FILE` o `update-ca-certificates`): no toca el código, pero amplía la confianza de todo el proceso (cualquier cliente HTTPS del API aceptaría esa CA), no se prueba en una prueba unitaria y depende de cómo se construya cada imagen. Descartado porque el alcance exacto de la confianza es lo que se quiere demostrar y acotar.
- **Desactivar la validación en el laboratorio** (`RemoteCertificateValidationCallback = true`): es lo que habría ocultado todos los fallos que esta decisión quiere detectar. Descartado.
- **Fijar la clave pública (pinning) en lugar de la CA:** obliga a tocar la configuración del API en cada renovación del certificado del proveedor. La CA cambia mucho menos.
- **Comprobar revocación del certificado del proveedor (CRL/OCSP):** añade una dependencia de red más a la ruta de autenticación sin cerrar un riesgo claro; el atacante que importa tendría que comprometer la CA o el DNS. Reabrible si la política de seguridad lo exige.
- **mTLS API→Keycloak ahora:** ver Decision; sin amenaza o mandato concretos añade rotación de otro certificado sin beneficio medible.

## Evidence
- 10 pruebas de TLS y arranque en `OidcProviderTlsTests` (más 4 de rotación y caída, ver ADR-026) contra un proveedor HTTPS real (Kestrel con certificados de una CA de prueba, sin simular el cliente): acepta una cadena de la CA configurada; la confianza de varias CA se suma; rechaza (401) una cadena de CA no configurada, sin lista alguna, un certificado de otro nombre y uno caducado; un fichero ausente, basura, en blanco o solo con clave privada impide el arranque. Las de aceptación y las de arranque estaban en rojo antes de implementar (7 de 11 en la primera ejecución) y verdes después. Comprobación de mutación: quitar el control del nombre hace fallar la prueba del certificado de otro nombre.
- Contra Keycloak 26.7.5 real, con el API leyendo por HTTPS: E2E autenticado 7/7 (inicio de sesión con PKCE, contrato del token, aislamiento entre sitios, matriz de roles, cierre de sesión) y 2/2 de rotación y caída del proveedor, con el emisor `http://127.0.0.1:8081`.
- Una primera versión del laboratorio publicaba también el emisor por HTTPS al navegador. Obligaba a cada persona a confiar en la CA (el navegador devolvía `ERR_CERT_AUTHORITY_INVALID` y el inicio de sesión no avanzaba), así que se descartó: el valor de la prueba está en el canal del API, que sigue siendo TLS validado.
- Antes de reconstruir la imagen del API el mismo laboratorio daba 401 con `IDX10500` (el API no confiaba en la CA): la confianza es lo que hace que funcione, no un efecto lateral.

## Cost and ownership
Una propiedad de configuración, un manejador de unas 50 líneas; en el laboratorio, un script de emisión y tres secretos. Recurrente: renovar el certificado del proveedor y, si cambia de CA, actualizar la lista. Responsable: la persona responsable del producto con operación de identidad.

## Consequences
- **Límites del laboratorio:** (1) el navegador usa HTTP en loopback, así que **no se ha probado un emisor HTTPS visto por navegadores** ni la confianza del navegador en una CA real; queda para la PKI real (tarea 3.3). (2) `start-dev` de Keycloak no puede apagar el listener HTTP (ignora `http-enabled=false` en modo desarrollo, confirmado en la documentación del servidor). (3) Que el perfil de producción de Keycloak (`start`, HTTP desactivado, base de datos externa) funcione igual **no está probado**.
- La CA del laboratorio y su clave viven en el disco del desarrollador y en el runner de CI; no son una PKI. La emisión, renovación y revocación reales siguen siendo la tarea 3.3 (EJBCA).
- Un certificado del proveedor caducado deja sin identidad a todos los usuarios cuando el API tenga que volver a leer el documento ([ADR-026](ADR-026.md)); debe haber alerta de caducidad en la operación.
- En producción el emisor será HTTPS y el navegador corporativo ya confía en la CA interna; el API lo hará por `Identity:TrustedCaPaths` o por el almacén del sistema.

## Reversion
Quitar `TrustedCaPaths` de `IdentityOptions`, `IdentityBackchannel.cs` y su uso en `IdentityRegistration`, y `lab-secrets/tls` del script y del overlay. Sin ella el certificado del proveedor debe encadenar a una raíz de la plataforma.
