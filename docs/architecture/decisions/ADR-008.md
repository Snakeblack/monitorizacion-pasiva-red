# ADR-008 — EJBCA y mTLS en todos los saltos; Keycloak para personas

**Estado:** Sustituido como decisión inicial por [ADR-010](ADR-010.md). **Fuente:** propuesta española pp. 5 y 9; caso inglés pp. 3–6 y 11–13.

## Contexto y criterios

Cada enlace interno debe cifrar y autenticar ambos extremos; certificados distinguen servicios, proxies, nodos y equipos. La persona requiere autenticación y permisos propios. TLS solo de servidor y un certificado de equipo no cubren esos dos objetivos simultáneamente.

## Decisión propuesta

EJBCA como PKI privada con raíz offline y emisora interna. Emitir perfiles cliente/servidor X.509 para sonda, Kafka, Registry, workers, API, balanceador, Keycloak, bases, telemetría, backups y equipos gestionados. En cada salto, validar cadena, SAN, EKU, vigencia y revocación mediante CRL/OCSP internos; automatizar provisión, renovación y alertas. Un proxy termina y reestablece mTLS al siguiente componente. Keycloak gestiona login OIDC Authorization Code + PKCE; API valida token y RBAC. ACL Kafka y roles de bases aplican mínimo privilegio.

## Alternativas y por qué no ahora

| Alternativa | Ventaja | Motivo para no seleccionarla |
|---|---|---|
| TLS con certificado solo de servidor | Despliegue más sencillo | No autentica al cliente; incumple la restricción propuesta para cada salto. |
| Una CA por componente | Aislamiento independiente | Aumenta raíces de confianza y operación de rotación/revocación sin necesidad demostrada. |
| PKI corporativa genérica | Reutiliza plataforma | Solo es opción si garantiza perfiles, identidades, ciclo y cobertura exigidos; de lo contrario no controla los contratos del sistema. |
| Solo mTLS, sin Keycloak | Menos IdP | Identifica equipo/servicio, no persona, roles ni acciones. |
| IdP SaaS / identidad propia | Menos operación / mayor control de código | SaaS contradice red privada propuesta; identidad propia aumenta riesgo y mantenimiento frente a Keycloak previsto por el caso. |

## Consecuencias y validación

La cobertura total eleva complejidad de bootstrap, almacenes de confianza, HA de PKI, navegador corporativo y rotación sin caída. Probar cada cliente/protocolo y cada salto real, incluida revocación. La matriz RBAC concreta sigue pendiente; no inferir que un certificado concede acceso a una operación.
